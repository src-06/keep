Keep

Keep

Nix tooling to enable declarative management of non-volatile system state.

Inspired and heavily influenced by impermanence but not meant to be a drop-in replacement.

Documentation

The full option reference and more examples are available in the documentation.

Prerequisites

Requires at least nixos-24.11 and a systemd-based initrd.

Why?

This aims to provide a declarative state management solution for NixOS systems without resorting to interpreters to do the heavy lifting. This should enable impermanence-like state management on an "interpreter-less" NixOS system.

Usage

State is preserved via keepTo, an attribute set whose attribute names are the persistent storage locations. An entry is active as soon as it has something to preserve, i.e. its dirs or files are non-empty — there is no enable switch. To disable an entry whose lists are populated by other modules, override them with empty lists:

keepTo."/state" = {
  dirs = lib.mkForce [];
  files = lib.mkForce [];
};

Multiple locations — and multiple users — can be configured side by side:

keepTo."/state" = {
  # system-level data, paths are absolute
  dirs = [ "/var/log" ];
  files = [ { file = "/etc/machine-id"; inInitrd = true; } ];
};

keepTo."/state/userdata" = {
  # user data of alice, paths are relative to alice's home dir
  username = "alice";

  # hide bind-mounts from desktop environments and file managers
  hideMount = true;

  dirs = [
    "Documents"
    "Projects"
    ".local/share/fish"
  ];
  files = [
    { file = ".config/foo"; method = "symlink"; }
  ];
};

Storage location options

Each keepTo."<path>" entry supports:

  • username: the user whose state is preserved. Defaults to root, i.e. system-level preservation with absolute paths. Any other user interprets dirs and files relative to that user's home dir and defaults ownership to that user.
  • hideMount: adds the mount options x-gvfs-hide and x-gdu.hide to every bind-mounted entry of this location.
  • dirs / files: the paths to preserve. Plain strings are accepted and coerced.

Per-path options

Every entry in dirs and files additionally accepts:

  • method: how the path is preserved, either bindmount (the default) or symlink.
  • user, group, mode: ownership and permissions on both volumes.
  • parent: ownership and permissions of the path's parent dir (enable, user, group, mode).
  • mkTarget: with method = "symlink", create an empty dir/file as the symlink's target on the persistent volume.
  • inInitrd: prepare the preservation already in the initrd.
  • mountOptions: additional mount options, only used for bindmounts.

Persisting the machine ID

/etc/machine-id needs special treatment to be preserved across reboots. The recommended setup uses a symlink and adapts systemd-machine-id-commit.service:

keepTo."/state" = {
  files = [
    { file = "/etc/machine-id"; inInitrd = true; method = "symlink"; mkTarget = true; }
  ];
};

systemd.services.systemd-machine-id-commit = {
  unitConfig.ConditionPathIsMountPoint = ["" "/state/etc/machine-id"];
  serviceConfig.ExecStart = ["" "systemd-machine-id-setup --commit --root /state"];
};

See the examples for details and alternatives.

keepTo

Specify multiple persistent storage locations to preserve state at.

Each attribute name is the path of a persistent storage root; the entry’s dirs and files are stored beneath it. Entries are independent: they may serve different users and apply different settings.

Type: attribute set of (submodule)

Default: { }

Example:

{
  keepTo."/keep/host_systems" = {
    # system-level, paths are absolute (username defaults to "root")
    enable = true;
    dirs = ["/var/lib/service"];
  };
  keepTo."/keep/user_data" = {
    # paths are relative to the user's home dir
    enable = true;
    username = "alice";
    dirs = ["Documents"];
  };
}

Type: boolean

keepTo.<name>.username

Specify the user for which dirs and files are preserved.

The default root configures system-level preservation: paths are interpreted as absolute paths and ownership defaults to root.

When set to any other user, paths are interpreted relative to that user’s home dir (home), and parent dirs on persistent storage are configured with the user’s ownership and permissions.

Multiple entries with different users may be configured side by side, each under its own attribute name (path).

Type: string, not containing newlines or colons

Default: "root"

Example: "alice"

Examples

See Configuration Options for all available options.

Entries under keepTo."<path>" are active as soon as their dirs or files are non-empty; there is no enable switch.

Simple

# configuration.nix
{
  config,
  lib,
  pkgs,
  ...
}:
{
  keepTo."/persistent" = {
    files = [
      # auto-generated machine ID
      { file = "/etc/machine-id"; inInitrd = true; }
    ];
    dirs = [
      "/var/lib/systemd/timers"
      # NixOS user state
      "/var/lib/nixos"
      "/var/log"
    ];
  };

  # systemd-machine-id-commit.service would fail, but it is not relevant
  # in this specific setup for a persistent machine-id so we disable it
  #
  # see the firstboot example below for an alternative approach
  systemd.suppressedSystemUnits = [ "systemd-machine-id-commit.service" ];

}

Compatibility with systemd's ConditionFirstBoot

In this example the machine-id is preserved on the persistent volume via symlink instead of a bind-mount. The option parent.enable causes the parent dir of the symlink's target, i.e. /persistent/etc/ to be created, and mkTarget creates an empty machine-id file at the target itself, enabling systemd's first boot semantics. Additionally, systemd-machine-id-commit.service is adapted to persist the tmpfs mount created by system to the persistent volume.

# configuration.nix
{
  config,
  lib,
  pkgs,
  ...
}:
{
  keepTo."/persistent" = {
    files = [
      # auto-generated machine ID
      { file = "/etc/machine-id"; inInitrd = true; method = "symlink"; mkTarget = true; parent.enable = true; }
      # ...
    ];
    dirs = [
      # ...
    ];
  };

  # let the service commit the transient ID to the persistent volume
  systemd.services.systemd-machine-id-commit = {
    unitConfig.ConditionPathIsMountPoint = [
      ""
      "/persistent/etc/machine-id"
    ];
    serviceConfig.ExecStart = [
      ""
      "systemd-machine-id-setup --commit --root /persistent"
    ];
  };
}

Complex

# configuration.nix
{
  config,
  lib,
  pkgs,
  ...
}:
{
  keepTo."/persistent" = {
    # hide bind-mounts from desktop environments and file managers
    hideMount = true;

    # preserve system dirs
    dirs = [
      "/etc/secureboot"
      "/var/lib/bluetooth"
      "/var/lib/fprint"
      "/var/lib/fwupd"
      "/var/lib/libvirt"
      "/var/lib/power-profiles-daemon"
      "/var/lib/systemd/coredump"
      "/var/lib/systemd/rfkill"
      "/var/lib/systemd/timers"
      "/var/log"
      { dir = "/var/lib/nixos"; inInitrd = true; }
    ];

    # preserve system files
    files = [
      { file = "/etc/machine-id"; inInitrd = true; }
      { file = "/etc/ssh/ssh_host_rsa_key"; method = "symlink"; parent.enable = true; }
      { file = "/etc/ssh/ssh_host_ed25519_key"; method = "symlink"; parent.enable = true; }
      "/var/lib/usbguard/rules.conf"

      # creates a symlink on the volatile root
      # creates an empty dir on the persistent volume, i.e. /persistent/var/lib/systemd
      # does not create an empty file at the symlink's target (would require `mkTarget = true`)
      { file = "/var/lib/systemd/random-seed"; method = "symlink"; inInitrd = true; parent.enable = true; }
    ];
  };

  # User-specific state gets its own storage location. Paths are interpreted
  # relative to butz's home dir; ownership and scaffold path components
  # default to butz.
  keepTo."/persistent/users/butz" = {
    username = "butz";

    files = [".histfile"];
    dirs = [
      # custom mode for a preserved dir
      { dir = ".ssh"; mode = "0700"; }
      ".config/syncthing"
      ".config/Element"
      ".local/state/nvim"
      ".local/state/wireplumber"
      ".local/share/direnv"
      ".local/state/nix"
      ".mozilla"
    ];
  };
}

Impermanence

Impermanence is the established solution for managing persistent state on NixOS systems. Keep is inspired and heavily influenced by impermanence.

See Comparison for a high-level overview of their differences.

How does Keep compare to impermanence

Keep does not attempt to be a very generic solution

Keep tries to fill a specific niche. For instance, Keep does not support non-NixOS systems via home-manager, which is supported by impermanence. See Migration for more technical details.

Keep only generates static configuration

That is configuration for systemd-tmpfiles and systemd mount units. This makes Keep a potential candidate for state management on interpreter-less NixOS systems.

Impermanence makes use of NixOS activation scripts and custom systemd services with bash (at the point of writing this), to create files and dirs, setup mounts and configure ownership and permissions (see next point).

Keep must be precisely configured

There is no special runtime logic in place. This means that the user must define:

  • when the preservation should be set up: either in the initrd, or after (the default)
  • how the preservation should be set up: either by symlink, or bindmount (the default)
  • whether or not parent dirs of the persisted files require special permissions

See Migration for specifics that need to be considered when coming from an impermanence setup.

Similar configuration

Keep's configuration is based on, and very similar to that of impermanence. See Migration for technical details.

No enable option

The keep module does not use an enable switch: an entry is active as soon as it has something to preserve, i.e. its dirs or files are non-empty. This differs from both impermanence and upstream preservation.

To disable an entry whose lists are populated by other modules, override them with empty lists (lib.mkForce []).

For thoughts on the enable option, see the discussion at https://github.com/nix-community/impermanence/pull/171 and for available configuration options see Configuration Options.

Generic hideMount option

Impermanence provides a hideMounts option, which sets the mount option x-gvfs-hide for bind-mounts. The keep module provides a similar hideMount option, which adds x-gvfs-hide and x-gdu.hide to the mount options of every bind-mounted entry.

Additionally, keep allows for the configuration of arbitrary mount options per file and dir via mountOptions.

Migration from impermanence to Keep

This section lists individual differences between impermanence and Keep, to better understand them in context of a complete configuration Examples may be helpful.

The following points need to be considered when migrating an existing impermanence configuration to Keep:

No global enable switch

An entry under keepTo."<path>" is active as soon as its dirs or files lists are non-empty. There is no separate enable option.

To disable an entry whose lists are populated by other modules, override them with empty lists:

keepTo."/state" = {
  dirs = lib.mkForce [];
  files = lib.mkForce [];
};

Handling of existing state

Coming from a setup with impermanence it is important to make sure existing persistent state is preserved correctly, meaning the ownership and mode of preservation remains the same. There is no exhaustive list of files and dirs requiring special treatment but at least the following needs to be considered:

SSH host keys

Correct ownership and mode of SSH host keys is very important for sshd to accept connections. Getting this wrong, e.g. not restricted enough, may cause your host to become inaccessible via SSH, forcing you to use other means of logging into the machine.

The following config may be used to preserve the RSA and Ed25519 host keys with Keep:

keepTo."/state".files = [
  { file = "/etc/ssh/ssh_host_rsa_key"; method = "symlink"; parent.enable = true; }
  { file = "/etc/ssh/ssh_host_ed25519_key"; method = "symlink"; parent.enable = true; }
];

The above config does not include access modes for the key files because the preservation mode is symlink and the link's target is not touched by preservation without an explicit mkTarget = true.

Secrets and other files requiring special access modes

Any files and dirs that need to have a mode that differs from the default (0644 for files and 0755 for dirs) must be configured explicitly to avoid having the default mode applied.

When to persist

Files and dirs that need to be persisted early, must be explicitly configured. For example /etc/machine-id:

This file needs to be persisted very early, by explicitly setting inInitrd to true:

keepTo."/state".files = [
  { file = "/etc/machine-id"; inInitrd = true; }
];

How to persist

The mode of preservation must be set explicitly for some files and dirs. This can be done by setting method to either symlink or bindmount (default). For most cases the default is sufficient but sometimes a symlink may be needed, for example /var/lib/systemd/random-seed.

This file is expected to not exist before it is initialized. A symlink can be used to cause its creation to happen on the persistent volume:

keepTo."/state".files = [
  {
    file = "/var/lib/systemd/random-seed";
    # create a symlink on the volatile volume
    method = "symlink";
    # prepare the preservation early during startup
    inInitrd = true;
  }
];

Note that no file is created at the symlink's target, unless mkTarget is set to true.

Scaffold path components

Any dir that is not preserved itself but is a parent of a preserved file or dir is called a scaffold path component here. Regarding the ownership and permissions of these scaffold path components, the following needs to be considered.

Scaffold path components of user-specific files and dirs

Parent dirs of a preserved user-specific file or dir are created with the respective user as their owner and permissions 0755. This is the case for all scaffold path components up to, but not including, the user's home dir.

Example

Consider the following preservation config:

keepTo."/state/userdata" = {
  username = "alice";
  dirs = [
    ".local/state/nvim"
  ];
};

This config will cause the module to configure a bind-mount for the subdir nvim, causing its contents to be preserved. The scaffold path components .local and state will be created if necessary, but their contents are not preserved. Owner is set to alice, group to alice's primary group, i.e. users.users.alice.group and the mode is set to 0755.

Scaffold path components of system-wide files and dirs

For system-wide files and dirs, missing components of a preserved path that do not already exist, are created by systemd-tmpfiles with default ownership root:root and mode 0755.

Should such dirs require different ownership or mode, the intended way to create and configure them is via systemd-tmpfiles directly.

Example

Consider a preserved file /foo/bar/baz:

keepTo."/state".files = [
  { file = "/foo/bar/baz"; user = "baz"; group = "baz"; };
];

This would create the file with desired ownership on both the volatile and persistent volumes. However, the parent dirs that did not exist before, i.e. /foo and /foo/bar, are created with ownership root:root and mode 0755.

Keep allows the configuration of immediate parents, so the permissions for /foo/bar can be configured:

keepTo."/state".files = [
  {
    file = "/foo/bar/baz"; user = "baz"; group = "baz";
    parent.enable = true;
    parent.user = "baz";
    parent.group = "bar";
  };
];

Now the parent dir /foo/bar is configured with ownership baz:bar. But the first path component /foo still has systemd-tmpfiles' default ownership and the configuration becomes quite convoluted.

Solution

To create or configure scaffold path components of a persisted path, systemd-tmpfiles may be used directly:

# configure preservation of single file
keepTo."/state".files = [
  { file = "/foo/bar/baz"; user = "baz"; group = "bar"; };
];

# create and configure parents of preserved file on the volatile volume with custom permissions
# The keep module also uses `settings.keep` here.
systemd.tmpfiles.settings.keep = {
  "/foo".d = { user = "foo"; group = "bar"; mode = "0775"; };
  "/foo/bar".d = { user = "bar"; group = "bar"; mode = "0755"; };
};

See tmpfiles.d(5) for available configuration options.

Library and Testing

Library

The functionality that is used in the module to discover the files and dirs that are persisted and to generate the corresponding tmpfiles config and mount units is available from lib.nix. It is also available from the flake lib output.

In both cases it needs to be instantiated with the nixpkgs lib.
